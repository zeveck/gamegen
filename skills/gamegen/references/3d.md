# 3D games

Read this only for a 3D game: one made with `--3d`, or whose request asked
for 3D in so many words (see SKILL.md). Everything in SKILL.md still applies:
the phases, the budget, the reviews, audio, the play-test, the polish pass and
publishing. This file says what's different. Give it to the design reviewers
and the final reviewers along with their roles.

The 3D models come from **meshgen** (Meshy): textured models from a picture
or a description, and rigged humanoid characters with animation clips. Each
asset is one GLB file in meters, standing on the ground (y = 0) and facing
+Z. Use it through its own skill (`/meshgen`) and follow its instructions;
its `reference.md` covers loading the GLBs in three.js and Godot, held items,
and clips versus code animation in more detail than this file. Its Mage
Playground (`examples/mage` in the meshgen repository) is a small working
three.js game built this way.

## Design

Add to the design (alongside the usual sections from design-template.md):

- **Camera:** third person behind the character, top-down, side-on or fixed,
  and how it follows. Third person turns with the mouse (drag, or pointer
  lock on desktop) and with a drag on the right side of a phone screen.
- **Controls** for 3D: movement relative to the camera, and on phones a
  virtual stick on the left and action buttons on the right.
- **Scale in meters:** the character's height (about 1.7 to 1.8 for a
  person), and sizes for props and the spaces they move through.
- **What moves how:** which characters are rigged humanoids with Meshy
  clips (only two-legged humanoids can be rigged), and which things are
  animated in code (animals, creatures, vehicles, doors, pickups).
- **Keep it small.** A few rigged characters and a dozen or so props make a
  good 3D game. Levels are built in code from those props plus simple shapes
  (floors, walls, terrain), not as one huge generated model.
- **The asset list** marks each 3D asset with tool `meshgen`, its height in
  meters, and its clips. Weapons and held items are separate models.

The Builder reviewer checks this too: what will be slow on a phone, and
whether every character the design rigs is really a two-legged humanoid.

## Assets

**Pictures first.** For characters and anything whose look matters, make a
concept picture with imagegen2 first, look at it, and then hand it to
meshgen (`--image`). meshgen keeps a picture's details far better than a
text prompt. A good picture shows one subject, full body, from the front, on
a plain background, with even light and no text. Characters stand in an
A-pose (arms angled down and away from the body), legs apart and visible,
hands empty. The style anchor for a 3D game is the main character's concept
picture; every other concept picture uses it as a reference. Text prompts
are fine for simple props.

The 2D tools still have jobs in a 3D game: nanogen for sky backdrops, ground
textures and the title art, imagegen2 for concept pictures and icons, and
audiogen for all the music and sound. anim8gen isn't used: Meshy animates
the characters.

**Where the files go.** Run meshgen from the folder with the `.env` (it
finds `MESHY_API_KEY` there), with `--dir` pointing at the game's candidates
folder:

```bash
node <meshgen skill folder>/meshgen.cjs character hero --image concepts/hero.png --height 1.8 \
  --actions idle,walk,run,jump,slash,hit,die --dir <game>/.gamegen/candidates/models
```

Each asset gets a folder with `<name>.glb`, `meshgen.json`,
`preview/sheet.png` and `source/` (Meshy's large raw downloads). Copy only
the accepted `<name>/<name>.glb` to `game/assets/models/`. The rest stays in
`.gamegen/`, which git already ignores.

**Look at every preview sheet** (`preview/sheet.png`) before accepting a
model: it looks like its picture, faces the red arrow (+Z), stands on the
ground at the right height, and every clip moves the way its name says. Read
the JSON's `warnings` too. Remake a bad one up to twice, then simplify.

**Budget.** Meshy charges credits, about $0.02 each. Every meshgen command
prints JSON with `creditsUsed` and `creditsLeft`: record each asset's credits
and their dollar value in `design/ASSETS.md`, against the same `--budget` as
everything else. Typical costs: about 30 credits for a prop, about 50 for a
character with 7 clips, 3 for each extra clip. `--dry-run` gives the cost
before spending, and `--max-credits <n>` stops a command that would cost more
than its share. Spending is pre-approved up to the budget, so agents making
models don't stop to ask (meshgen otherwise asks first).

**Size.** A character GLB is about 6 MB and a prop 1 to 4 MB, so a 3D game
is much heavier than a 2D one. Keep the count down, keep meshgen's default
texture size (1024 px), and use one character model for several characters
of the same kind.

## Building for the web

The web game rules in web-target.md all still hold: no build step, nothing
from the internet at runtime, the service worker, installing, the debug hook,
and "Looking finished". On top of them:

- **three.js, vendored.** Copy the three.js that meshgen ships (MIT:
  `viewer/vendor/` in the meshgen skill folder, with its LICENSE and the
  `addons/` it uses) into `game/vendor/`, and load it with an import map,
  no CDN. Use that copy rather than a newer one: meshgen's previews were
  checked with it, and three.js often changes between versions. Each game
  keeps the copy it was built with.

  ```html
  <script type="importmap">
  { "imports": { "three": "./vendor/three.module.js", "three/addons/": "./vendor/addons/" } }
  </script>
  ```

- **Loading models:** `GLTFLoader`. Show a loading screen with progress
  while the models arrive (they're big), and keep the title still until
  they're in (see "The first load" in web-target.md).
- **Animation:** one `AnimationMixer` per character. Crossfade between idle,
  walk and run by speed (about 0.2 seconds). Other clips (jump, slash, hit,
  die) are one-shots: play once, then fade back when the mixer's `finished`
  event fires. Time the game's events (the frame the sword hits) as a
  fraction of the clip, read from the preview sheet.
- **Clips play in place:** the game moves the character, and turns it to
  face where it's going (`rotation.y = Math.atan2(dir.x, dir.z)`, since
  models face +Z).
- **Held items:** separate meshgen models attached to the `RightHand` or
  `LeftHand` bone (the rig is often scaled by 0.01, so undo that scale on a
  holder group; meshgen's reference.md shows how).
- **Effects in code:** flames, glows, projectiles, sparks and hit flashes are
  particles, sprites and lights, not models.
- **Unrigged things** (props, animals, vehicles) are animated in code:
  bobbing, spinning, swaying, simple tweens.
- **Several copies of one character:** `SkeletonUtils.clone(gltf.scene)`, each
  with its own mixer. A plain `.clone()` breaks the skinning.
- **Camera:** a camera-relative third-person controller (or whatever the
  design chose) that keeps the character in view and doesn't go through
  walls.
- **Phones:** cap the pixel ratio (`renderer.setPixelRatio(Math.min(devicePixelRatio, 2))`),
  keep shadows to one light with a small shadow map, and keep the HUD and
  menus in HTML over the canvas, so the text scanner can read them.

## Play-testing 3D

Headless Chromium draws WebGL in software, at a few frames a second, so
waiting for wall-clock time doesn't work: a jump that takes half a second can
take ten. The game controls time instead. Add a `step` to the debug hook:

```js
window.__game.step = (seconds) => {
  // fixed updates of 1/30 s, then one render
  for (let t = 0; t < seconds; t += 1 / 30) update(1 / 30);
  render();
  return window.__game.state();
};
```

The game's own loop keeps running for players; the play-test presses and
holds keys (or touches) as usual, then calls `step` to move time on, then
takes the screenshot. Record each level's solution as inputs with step
lengths rather than wall-clock timings, and replay it the same way.

`playwright-cli eval` wraps what it's given as a single expression, so
several statements need a function that's called straight away:

```bash
playwright-cli -s=desktop eval "(() => { window.__game.step(1.5); return JSON.stringify(window.__game.state()); })()"
```

The first-load filmstrip and the text scanner work as for any web game.
Look at 3D screenshots for: characters floating above or sunk into the
ground, facing the wrong way, held items in the wrong hand or angle, the
camera inside a wall, and things too dark to see.

## Godot 3D

With `--target godot` and a 3D request (see other-targets.md for the rest):

- Put the GLBs in `res://models/`. Godot imports each as a scene with an
  `AnimationPlayer` holding every clip, already in meters, +Y up and facing
  +Z.
- Set the loop mode for idle, walk, run and other cycles (meshgen marks
  them with `extras.loop`): in the import settings, or in code with
  `anim.get_animation("idle").loop_mode = Animation.LOOP_LINEAR`.
- Attach held items with a `BoneAttachment3D` under the `Skeleton3D`, set to
  `RightHand` (or `LeftHand`), with the item's scene under it.
- Use an `AnimationTree` or simple code to blend idle, walk and run.
